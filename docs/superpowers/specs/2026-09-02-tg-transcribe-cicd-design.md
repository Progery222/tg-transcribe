# tg-transcribe: архитектура Git, CI/CD и Coolify

Дата: 2026-09-02
Статус: черновик для проверки перед внедрением

## 1. Назначение и границы

Документ описывает безопасную схему разработки, проверки, публикации и развертывания сервиса `tg-transcribe`.

В область работ входят:

- локальная разработка в `C:\Projects\Серваки\tg-transcribe`;
- репозиторий GitHub `Progery222/tg-transcribe`;
- production-развертывание сервиса в Coolify;
- работа с исходниками и серверной диагностикой через отдельные контексты Orca;
- автоматическое развертывание после принятия изменений в ветку `main`.

Проект `F:\Projects\FarmTransfer` в эту настройку не входит и не изменяется.

## 2. Зафиксированное состояние системы

Локальная папка `C:\Projects\Серваки\tg-transcribe` является корнем исходного Git-репозитория: в ней находятся `.git`, `.github`, `src`, `tests`, `Dockerfile`, `pyproject.toml` и файлы Compose.

Локальная ветка называется `main`. На момент проектирования она содержит один локальный коммит, которого ещё нет в `origin/main`. Перед первой публикацией нужно отдельно проверить содержимое этого коммита и только после этого отправлять его в GitHub.

В репозитории сейчас есть workflow `.github/workflows/deploy.yml` с тремя стадиями:

1. проверка зависимостей, линтер и тесты;
2. сборка и публикация образа в GHCR;
3. перезапуск через self-hosted runner.

Целевой self-hosted runner GitHub находится в состоянии `offline`, поэтому текущий deploy-job может оставаться в очереди и не является надёжным способом публикации.

Фактический production уже управляется Coolify. Активный ресурс называется `tg-transcribe`, находится в проекте Coolify `telegram-bots` и запускается из `docker-compose.coolify.yml`. Работающие контейнеры имеют метку управления Coolify. Это означает, что запуск отдельного `docker compose` из `/home/atom/tg-transcribe` в обычном процессе опасен: он может создать второй экземпляр бота с теми же секретами и Telegram-токеном.

## 3. Целевая архитектура

Единственным источником исходного кода является GitHub:

```text
локальная папка / Orca local
        |
        | feature-ветка -> Pull Request
        v
GitHub: Progery222/tg-transcribe
        |
        | обязательный CI перед merge
        v
ветка main
        |
        | штатный webhook/integration Coolify
        v
Coolify: telegram-bots / tg-transcribe
        |
        v
production на сервере
```

Роли компонентов:

- локальная папка — редактирование кода, запуск локальных тестов и разработка;
- GitHub — история, ветки, Pull Request и точка принятия изменений;
- GitHub Actions — только CI и проверка Docker-сборки;
- Coolify — единственный штатный CD-контроллер production;
- серверный Orca-контекст — диагностика, логи, состояние контейнеров и операционные действия в пределах конкретного сервиса.

## 4. Контексты Orca

Для сервиса используются два разных контекста:

### 4.1. `tg-transcribe — исходники`

- Локальный путь: `C:\Projects\Серваки\tg-transcribe`.
- Назначение: разработка, чтение и изменение исходников, тесты, Git, Pull Request.
- Основной агент: Codex или Claude в зависимости от задачи.
- Рабочая ветка: feature-ветка; `main` не используется для незавершённой разработки.

### 4.2. `tg-transcribe — сервер`

- Удалённый путь: `/home/atom/tg-transcribe`.
- Назначение: диагностика сервера и ручные операционные действия.
- Этот контекст не является вторым источником исходников.
- Файлы production, которыми управляет Coolify, находятся в его artifact-директории и не должны редактироваться вручную как способ доставки кода.

Изменения переносятся между контекстами не копированием файлов, а через GitHub и Coolify. Прямая синхронизация `rsync`, `scp` или ручное копирование локальной папки на сервер не используется в штатном процессе.

## 5. Рабочий процесс разработки

Для каждой задачи применяется следующий порядок:

1. В локальном контексте получить актуальный `main` из GitHub.
2. Создать отдельную feature-ветку от актуального `main`.
3. Попросить агента сначала изучить релевантный код и тесты, затем внести минимальное изменение.
4. Запустить локальные проверки.
5. Создать коммит с понятным сообщением.
6. Отправить feature-ветку в GitHub и открыть Pull Request.
7. Дождаться обязательного CI и проверить diff.
8. После принятия Pull Request выполнить merge в `main`.
9. Дождаться одного deployment в Coolify и проверить состояние сервиса.

Production не изменяется из незакоммиченных файлов и не обновляется из произвольной рабочей ветки.

## 6. Контракт CI

Workflow GitHub Actions должен запускаться для Pull Request в `main` и для push в `main`.

Обязательные проверки:

- установка Python 3.12 через `uv`;
- `uv sync --frozen`;
- `uv run ruff check .`;
- `uv run pytest -v`;
- проверка сборки Dockerfile без публикации образа и без доступа к production.

CI не должен:

- подключаться к серверу по SSH;
- зависеть от self-hosted runner;
- менять Coolify;
- перезапускать production;
- публиковать образ в GHCR как часть основного production-пути, если Coolify собирает образ из Git-репозитория.

Текущие стадии `build-and-push` и `deploy` следует убрать из основного workflow. Публикация в GHCR оставляется только как отдельная будущая стратегия, если будет принято решение перевести Coolify на immutable image deployment. Одновременное использование GHCR-деплоя и сборки Coolify не допускается.

Для GitHub Actions достаточно минимальных прав, необходимых для чтения исходников и выполнения проверок. Production-секреты и SSH-ключи в Actions не передаются.

## 7. Контракт CD и Coolify

Production-ресурс Coolify должен быть настроен следующим образом:

- проект: `telegram-bots`;
- ресурс: `tg-transcribe`;
- источник: Git-репозиторий `Progery222/tg-transcribe`;
- production-ветка: `main`;
- Compose-файл: `docker-compose.coolify.yml`;
- автоматический deploy: включён для изменений в `main`;
- один активный production-ресурс для этого Telegram-бота.

Coolify должен получать изменения после merge в `main` через штатную GitHub-интеграцию/webhook, затем собрать `Dockerfile` согласно `docker-compose.coolify.yml` и перезапустить только принадлежащие этому ресурсу контейнеры.

В рамках внедрения перед первым deploy нужно проверить в UI Coolify фактический URL репозитория, ветку, путь Compose-файла, переменные окружения, домены/маршруты при их наличии и статус auto-deploy. Нельзя запускать ручной Compose-деплой параллельно этой проверке.

## 8. Секреты, данные и тома

`.env` хранится только в Coolify/server environment и не добавляется в Git. В Git также не попадают Telegram-токены, API-ключи, SSH-ключи, cookie и локальные файлы сессий.

Именованные Docker volumes из `docker-compose.coolify.yml` считаются постоянными данными production. Обычный redeploy не должен их удалять.

Запрещено использовать `docker compose down -v` для штатного обновления или диагностики. Перед изменениями Compose нужно убедиться, что имена volumes и обязательные переменные сохраняются.

## 9. Откат и восстановление

Основной откат выполняется в Coolify через историю deployments: выбирается предыдущая рабочая ревизия и выполняется redeploy.

Перед merge желательно сохранить ссылку на текущий успешный deployment и commit SHA. После неудачного deploy проверяются логи только ресурса `tg-transcribe`, затем выполняется rollback на последнюю успешную ревизию.

`docker-compose.prod.yml` и GHCR-образ рассматриваются как аварийный/legacy-путь. Они не используются параллельно с активным Coolify-ресурсом без отдельного решения оператора, потому что ручной запуск может привести к двум экземплярам одного бота.

## 10. Правила работы агентов

Для локального контекста агенту разрешены чтение и изменение исходников проекта, локальные тесты и операции Git в пределах репозитория.

Для серверного контекста агент по умолчанию выполняет read-only диагностику. Операции `pull`, `up`, изменение переменных окружения, миграции, удаление контейнеров/volumes и рестарт production требуют отдельного явного запроса с указанием точного ресурса и ожидаемого результата.

Перед любой серверной операцией агент обязан:

1. подтвердить текущий путь и ресурс;
2. определить, управляется ли ресурс Coolify;
3. проверить, не создаётся ли дубликат сервиса;
4. описать план и точную команду;
5. после действия проверить контейнеры и логи.

## 11. Критерии приёмки

Архитектура считается внедрённой после выполнения всех условий:

- локальный репозиторий и GitHub используют один источник исходников;
- feature-ветка и Pull Request проходят CI;
- `main` защищён обязательной успешной CI-проверкой перед merge;
- после merge в `main` запускается ровно один Coolify deployment;
- GitHub Actions не ждёт offline self-hosted runner и не выполняет SSH-deploy;
- Coolify использует `docker-compose.coolify.yml` и актуальную ревизию Git;
- production volumes и `.env` сохраняются после redeploy;
- после deploy бот и Telegram Bot API работают, а в логах нет немедленного циклического падения;
- rollback на предыдущий успешный deployment проверен или документирован с точными шагами;
- локальный и серверный Orca-контексты однозначно разделены.
